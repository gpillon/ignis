# ADR 0012 — Internal tracing spans reuse `request.id` as the OTel `trace_id`

## Status

Accepted (2026-09-07, grilling session on `.scratch/Ignis Structured Logging
Specification.md`).

## Context

The logging spec requires (§19) that `trace_id`/`span_id` be populated only
from a genuine active trace context, never fabricated. Ignis is a
single-process engine (no microservices), so cross-service distributed trace
propagation (incoming `traceparent` headers) is not the actual need. The
project owner's actual requirement is narrower and concrete: know, per
request, which internal stages it traversed (admission, prefill, one or more
**decode rounds** — the existing glossary unit a decode CUDA graph is
captured over, per `CONTEXT.md` — MTP verify, completion).

Ignis already has a `request.id` concept in the admission/fairness machinery
(`crates/core/src/admission.rs`, `crates/core/src/concrete.rs`). Introducing
a second, independent trace identifier generated by `tracing`'s span
machinery would give every request two IDs to grep for the same causal unit.

## Decision

- Fase 4 (tracing) instruments a **hierarchical span tree per request**: a
  root span opened at HTTP ingress (via `tower-http`'s `TraceLayer` on the
  `axum` server), with child spans for admission, prefill, each **decode
  round** (not per-token — per-token spans would themselves become hot-path
  logging overhead, violating §26), MTP verify, and completion.
- The OTel `trace_id` carried on log records **is** the existing
  `request.id`, not a separately generated ID. This is not fabrication per
  §19: the trace context is genuinely created by ignis's own instrumentation
  at request entry, it is simply keyed by an ID the fairness system already
  assigns.
- Spans are scoped to occur only at request/round granularity, i.e. outside
  the true per-token hot loop, so entering/exiting a span does not add
  measurable cost to the decode inner loop. Any span added inside the
  per-token path (as opposed to per-round) requires re-validation against the
  G4 performance gate (ADR 0007, ADR 0011) before merge — this is a hot-path
  performance decision, not just a tracing-API decision.

## Consequences

- One identifier (`request.id`) is sufficient to correlate admission
  decisions, prefill/decode structured logs, and (once fase 4 lands) span
  timing — across `grep`, log aggregation, and any future OTel export.
- If ignis ever needs genuine distributed tracing (e.g. a future
  multi-process/multi-node deployment), `request.id` reuse as `trace_id` may
  need revisiting, since external `traceparent` propagation expects a
  128-bit ID with specific generation rules ignis does not currently enforce
  on `request.id`. That is out of scope until such a deployment exists.
