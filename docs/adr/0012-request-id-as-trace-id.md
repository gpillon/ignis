# Internal tracing spans reuse `request.id` as the OTel `trace_id`

Each request gets a hierarchical span tree, a root span opened at HTTP ingress with child spans for admission,
prefill, each decode round and completion, and the OTel `trace_id` on its log records is the request's existing
`request.id`, not an id generated for tracing. What the owner needs is to know, per request, which internal stages it
went through; ignis is a single-process engine, so propagating a trace across services (an incoming `traceparent`
header) is not that need, and the admission and fairness machinery already gives every request an id. A `trace_id`
or `span_id` is populated only from a genuine active trace context, never fabricated, and this is not fabrication:
the context is created by ignis's own instrumentation at request entry, and is only keyed by the id the fairness
system already assigns.

Spans open at request and round granularity only, outside the per-token hot loop, so that entering and leaving one
adds no measurable cost to the decode inner loop: a span per token would itself be the hot-path logging overhead
that normal operation must not have. A span inside the per-token path, as opposed to per round, is a hot-path
performance decision, not only a tracing-API one: its cost to decode speed must be measured before merge, ignis
against ignis as ADR 0082 states for a speed claim (a branch against main, at least two launches per build), where
the 99% performance gate against the reference stood when this was decided, the rule ADR 0011 sets for a log event
on the same path.

## Considered Options

- **A second, independent trace identifier generated by `tracing`'s span machinery**: rejected. Every request would
  have two ids to grep for the same causal unit.

## Consequences

- One identifier is enough to correlate a request's admission decisions, its prefill and decode log records and its
  span timing, across `grep`, log aggregation and any future OTel export.
- If ignis ever needs genuine distributed tracing, a deployment of several processes or nodes, the reuse may need
  revisiting: external `traceparent` propagation expects a 128-bit id with generation rules ignis does not enforce on
  `request.id`. That is out of scope until such a deployment exists.
