# Every route has a deadline, and a passed one answers what was generated

Every route that runs the model holds a request to a deadline, one for an answer awaited whole and one for a stream,
and `0` is none. A passed deadline answers what was generated, ended as a length limit ends an answer, unless the
operator asks for an error (`server.timeout_reply`: `partial`, the default, or `error`). An inference engine is
expected to leave a request to its own end: a deadline is there to end what a wedged engine holds, and a whole
answer thrown away for being late helps no client, since the retry generates it again from nothing. So the default
is long enough for an agent's long reasoning step. The three fields are live, read per request, and keep a ceiling
against a fat-fingered value: whoever wants no deadline says `0`. What each route answers is in the guide
(`docs/user/api/deadlines.md`).

- **Counted from when the request starts to use the engine**: its admission, never a WebSocket's queue; an image
  job's turn, never its queue; a decision's question from its submission. A request waiting for a lane or in a queue
  has used none of the engine. A chat request's media acquisition is held to the whole-answer deadline from its own
  start, and with none only each fetch's own timeout bounds it.
- **A passed deadline cancels the engine request**, on every route, which frees its lane, and the request log says
  the cause was a timeout whatever answered the client. A wedged engine is still bounded: the answer is what reached
  the client, and the lane is freed once the model thread runs again.
- **Before any ending the client gets what the loop guard held back** (ADR 0052) and the tokens already waiting on
  the request's stream. Nothing waits on the engine itself, which may be what is wedged. A stop sequence those
  tokens complete ends the answer `stop`, as it would have before the deadline.
- **The cut reads as `length`, and as `incomplete` with `max_output_tokens` on the Responses API**: the only values
  the two APIs define for an answer cut by a limit, which a client handles today, and another engine already
  reports its own model-length limit as `length`. The deadline stays
  distinguishable where it matters: a header on an answer sent whole, the request log on every one. A stream sent
  its headers before the deadline, so only the log tells there.
- **Under `error`, a stream that already answered `200` ends with the `504`'s body as an error chunk and no finish
  chunk**, as a stream already ends for an engine error: a client that reads one reads the other.
- **A decision and an image are errors either way.** A decision's answer is one readout of one position, with no
  partial readout to return. An image cut between two denoising steps is noise, not a smaller image; a streamed
  job's completed images have gone out, and the error follows them.
- **A tool call that a `length` ending stops before it closes reaches the client as generated**: its name and the
  arguments written so far, as OpenAI's API returns one, whether the generation cap or a deadline under `partial`
  cut it; on the Responses API it is a `function_call` item with `status: "incomplete"` in an `incomplete`
  response. `length` already tells the client the answer is incomplete, so a client is never told that a call
  happened when it did not complete, and a JSON answer the cap cuts is returned as generated too. The arguments are
  the prefix of the JSON the closed call would have had, as far as the written text determines it. Every other
  ending (a stop sequence, a cancel, a disconnect, an engine error, a deadline under `error`) drops an open call
  whole, since `stop` would call it complete, and a call cut before its function name closes has nothing to name
  and is dropped. A cut call is not counted among the tool calls (ADR 0094).

## Considered Options

- **One deadline for every route.** Rejected: a stream and an answer awaited whole are read differently, and one
  field would force the same bound on both.
- **A `timeout` finish reason.** Rejected: neither API defines it, and a strict client reads an unknown finish as a
  failure and retries.
- **An error by default.** Rejected: a long answer thrown away at its deadline is regenerated by the retry; what was
  generated is worth more to the client than a `504`.

## Consequences

- A Responses WebSocket keeps an `incomplete` response for `previous_response_id`, as it keeps one a length limit
  ended: the next turn continues from it.
- A chat completion the engine drops, its stream closing without a finish, is an engine error, never a timeout.
