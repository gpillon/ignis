# ignis — project review, root problems, reorganization, path to a usable engine

Date: 2026-09-05. Scope: the whole repo (`crates/*`, `kernel/`, `docs/`,
`.scratch/*/specs`, `PENDING.md`, `KERNEL-WIP.md`) read against the reference
(`F:/ai/q38/ninfer`, ~92K lines C++/CUDA, Apache-2.0) and the real artifact
(`qwen3_8_27b_nvfp4full-v2.ninfer`). Evidence is cited as `file:line`.

---

## 0. Verdict (TL;DR)

1. **The engine has never produced a real completion, and it cannot on the
   current path.** `KERNEL-WIP.md` attributes this to one launch bug (#35). The
   launch bug is real, but it is the *shallowest* of at least eight
   correctness defects in the forward pass. Fixing #35 yields a forward that
   still computes the wrong function (wrong weight scales, wrong GDN gating,
   wrong RoPE positions, wrong state shape, missing norms).
2. **The compute architecture is inverted.** Activations, KV cache and GDN
   state live in host `Vec<u16>`; every op is an FFI call that H2Ds its inputs
   and D2Hs its outputs; residual/SiLU/readout are host loops. This is not a
   "for now" that gets optimized later — it is a different program. ninfer
   streams ~15.85 GB/token of weights in ~13 ms; ignis would move the
   per-request KV cache (hundreds of MB) and the GDN state (1.2 GB bf16 flat)
   over PCIe **per layer per token**. Expected gap: 2–3 orders of magnitude,
   before kernel quality.
3. **The kernels are naive scalar rewrites, not ports.** One-block-per-row
   scalar GEMV, 16×16 shared-memory scalar GEMM, decode attention that does a
   block reduce *per key* in a serial loop, a 1024-thread smem-reduced GDN
   step. ninfer's equivalents are warp-MMA / TMA / tensor-core split-KV /
   register-tiled warps, already at or near roofline. The "faithful
   adaptation" provenance comments are not accurate.
4. **The CUDA-graph "decode hot path" is not the model.** The captured graph
   is embed → *one* attention kernel → *one* GDN step → final norm → lm_head,
   over zeroed state with no layers and no projections
   (`kernel/src/decode_graph_surface.cu:19-25`). `decode_step` routes every
   batch-1 request through it (`compute.rs:3282-3287`), so the "hot path"
   would serve logits unrelated to the prompt.
5. **The Rust core (scheduler, paged KV pool, admission, host tier, prefix
   reuse) is a self-consistent CPU model that is not connected to any device
   memory.** `KvPool`/`BlockTable` are never referenced by `compute.rs`; the
   compute adapter keeps its own per-request host `kv_cache` + `block_table`.
   215 CPU tests pass; 26 GPU tests are `#[ignore]`d and self-skip. Green
   `cargo test` currently proves nothing about inference.
6. **Reorganization is needed — but not of the repo layout.** The workspace
   shape (Rust crates + C++/CUDA leaf behind a C ABI) is fine. What must
   change is the **level of the ABI** (per-step, device-resident, not per-op
   with host pointers), the **ownership of the forward pass** (a C++ program
   layer, like ninfer's `text_context_impl.h`), and the **kernel policy**
   (actually port ninfer's kernels, verbatim, with their layouts — or write
   tensor-core kernels; never scalar stand-ins).
7. **Honest distance to "at least what ninfer does":** ninfer is ~55K lines
   of ops + ~30K of runtime/targets/serve, tuned over months. Reaching its
   MTP0 decode (75 tok/s) and prefill (~8.5K tok/s @24K) with hq-e8-2b, prefix
   reuse, KV-RAM tier, MTP/DFlash2 is realistically **4–6 months** of focused
   work with agent assistance and a GPU-in-the-loop test discipline, *if* the
   kernels are ported rather than reinvented. The current process (specs →
   agent → CPU-green → "resolved") produced ~28K lines of Rust in 4 days and
   zero working inference; it must change before more code is written.

## 2. Correctness defects in the forward pass (all must be fixed for a "sane" output)

Each item is independent; #35 is only the first.

1. **GDN step launch invalid at 27B geometry** (`blockDim.x = 2048 > 1024`)
   — GitHub #35, `gdn_step.cuh`. Known.
2. **NVFP4 scale plane read with the wrong layout.** The artifact stores
   scales in `blockscale-k16-m128x4-v1` (swizzled 512-byte tiles:
   `storage-layouts.md` §4); the kernels index scales as row-major
   `[m][k/16]` (`nvfp4_gemm_decode.cuh:74`, `nvfp4_gemm_prefill.cuh:120`).
   Every NVFP4 GEMM (247 parents, ~85% of the weights) multiplies by the
   wrong group scale. `PENDING.md` (#30 notes) acknowledges this as "later
   re-implementation material" — it is a correctness bug, not perf.
3. **`weight_divisor` not applied.** The dequant is
   `e2m1 × e4m3 / weight_divisor` (`storage-layouts.md` §4, `normalize.rs`
   header: `coeff = e4m3_scale * 1/divisor`); the kernels compute
   `e2m1 × e4m3` only. Weights are off by `2688/amax` per tensor.
4. **GDN gating math wrong.** ninfer: per value head `h`,
   `g = -exp(A_log[h]) * softplus(a[h] + dt_bias[h])`, `beta = sigmoid(b[h])`
   (`ninfer/src/ops/kernel/gdn_gating.cuh:19-28`). ignis: `alpha = exp(a_raw)`
   with `a_raw` = the *first* of 48 a-rows and `beta` = the first b-row,
   shared across all 48 heads (`compute.rs` forward_layers: "the first a /
   first b of the 96-row a_b_projection"); `a_log`/`dt_bias` are loaded and
   unused.
5. **GDN state shape / precision wrong.** Model: 48 value heads × FP32
   `[128][128]` per layer, key head = value head / 3. ignis: one flat bf16
   `[6144][2048]` matrix per layer, a 2048-wide dot mixing all 16 key heads
   (`KERNEL-WIP.md` §3). Structurally a different recurrence.
6. **GDN gated RMSNorm missing.** ninfer applies `gated_rmsnorm` with
   `gdn/norm [128]` (per head) and the z gate before `gdn/output`
   (`text_context_impl.h` gdn_mix). ignis multiplies readout × z only.
7. **RoPE position advanced per layer.** `req_state.seq_pos += 1` inside the
   layer loop (`compute.rs` forward_layers end): token `i` at layer `l`
   rotates at `i*64 + l`, documented as the "pos contract". The model rotates
   every layer at position `i`. Attention over the prompt is scrambled.
8. **GQA output gate ignored.** The fused `query_key_gate_value` has gate rows
   (8192..14336) that sigmoid-gate the attention output; ignis projects and
   drops them (`PENDING.md` #30 fidelity notes). Also q/k norm is per-head
   but `key_norm`/`query_norm` are applied correctly only if the fused-plane
   row order matches — unverified (§3.2 "Fused parent row order" in
   `qwen3.8-27b-artifact.md` is not referenced anywhere in ignis).
9. **No EOS / stop-token handling.** Decode stops only on `max_tokens`
   (`compute.rs:2493-2507`, `3351`). Every completion runs to the cap.
10. **The decode graph path is not the model** (§0.4): batch-1 decode returns
    logits from a 5-kernel toy graph over zero state.

Consequence: the "sane output" floor (ADR 0005/0007) is unreachable on
this path. There is no partial credit: any one of 2, 3, 4, 5, 7 alone makes
the output noise.

## 3. Performance structure: why the current path cannot approach the 99% gate

### 3.1 Data movement (the architecture)

- Per request, `RequestState` holds on the **host**: the full paged KV
  (`num_blocks × num_kv_heads × block_size × 256 × 2 planes` bf16), the GDN
  state (48 × 6144 × 2048 bf16 = **1.2 GB**), conv state
  (`compute.rs:1216-1245`).
- `ignis_gqa_attention_decode` takes host pointers and H2Ds the whole KV
  buffer each call (`ignis_kernel.h:28`, "All buffer pointers are host
  memory"). 16 attention layers × per token.
- `ignis_gdn_step` H2Ds/D2Hs the layer's state slice: 48 × 25 MB in + 25 MB
  out per token = **2.4 GB of PCIe traffic per decode token** for GDN alone.
- The GDN readout `S^T k` is a host loop over 6144 × 2048 f32 per layer
  (`state_readout`, `compute.rs:2517`): ~600 M FMAs on the CPU per token.
- Residual add, SiLU×up, final norm loops: host.
- No streams (`stream = null` everywhere), no async copies, no pinned host
  memory, synchronous `cudaMemcpy` inside every leaf call.

Rough floor per decode token on this design: seconds, not milliseconds.
ninfer: 13.1 ms (MTP0). The gap is not a kernel-tuning gap.

### 3.2 Kernel quality (per op, vs the reference)

| Op | ignis | ninfer | Gap |
|---|---|---|---|
| NVFP4 GEMV (decode) | 1 block/row, scalar E2M1/E4M3 decode per element, `switch`-based, byte loads | warp-MMA rowsplit, vectorized 512-element tiles, shared-staged, PDL; BF16 GEMV at 90% of HBM BW | ~10–30× |
| NVFP4 GEMM (prefill) | 16×16 tile, fp32 smem, scalar FMA, bf16 activations | W4A4 tensor-core MMA + TMA at 52–59% of FP4 peak (1676 TFLOP/s); A4 activation quant with site divisors | ~50–100× |
| GQA decode attention | 1 block/head, serial loop over keys, `__syncthreads` block reduce **per key** | tensor-core split-KV, online softmax, bf16/int8/hq KV sources, at roofline @260k | ~100× at long context |
| GQA prefill attention | (not inspected in detail; same scalar style) | bf16/i8 tensor-core causal, 1024-token chunks | large |
| GDN step | 1 thread/column, 1024+ threads, smem reduce | warp-tiled 128-d_k per warp, register state, shuffles, `__launch_bounds__(128,2)` | ~10× + invalid launch |
| GDN prefill | per-token recurrence loop in Rust | chunked kernels (`prepare_wy_wu`, `state_passing`, `output`) on tensor cores | ~100× |
| KV cache | bf16 paged, host-resident | hq-e8-2b (HyperQuant) / int8 / bf16, device paged, exact-key side store | feature gap |
| lm_head | bf16 dequant of W8 (2.5 GB VRAM), bf16 GEMM | W8G32 GEMV streaming 1.35 GB | 2× bytes |
| Launch structure | ~one FFI + 2 memcpy per op | ~630 kernels in one CUDA graph per decode round, PDL chains | — |

### 3.3 Batching

`decode_step` runs the N lane jobs **serially** (`compute.rs:3289-3292`);
`prefill_step` too. ninfer's core invariant is "maximal batched decode: one
model traversal for all B decode-ready requests"
(`concurrent-inference-architecture.md` §2.1). Without batched decode, N=8
lanes divide throughput by 8 instead of amortizing weight reads. The "batched
prefill" of B1 is batching *tokens of one request* (multi-token GEMM), which
ninfer also does (chunked prefill) — it is not the north-star "concurrent
prefill across requests" experiment.

## 4. Process / documentation debt (why this happened, what to change)

1. **"Green" is decoupled from "works".** Every GPU test is `#[ignore]` and
   self-skips on any kernel error. Tickets were closed on CPU-green +
   synthetic geometry (`state_cols = 8`, vocab 256). The real geometry was
   never exercised until the last ticket. Rule to adopt: **no kernel/compute
   ticket closes without a GPU-run numeric check at real geometry against an
   oracle** (§6.1). "Skip = green" is retired for compute work.
2. **Provenance claims are inaccurate.** Kernel headers say "faithful
   adaptation … ported 1:1"; the ported part is the E2M1 table. A reviewer
   trusting the header would not open ninfer's file. Rule: a port claim must
   name the source file and be diffable; anything else is "own
   implementation".
3. **Over-claimed status.** README: "v1 is code-complete; the next milestone
   is the 99% gate". PENDING: "the decode graph is now the decode hot path".
   Neither is true. The ledger has become a record of tickets *closed*, not
   of capabilities *working*.
4. **Ticket granularity produced glue, not an engine.** The A1/A2/A3/B1/B2
   split was "make each op callable" then "assemble". Each op was validated
   in isolation with synthetic shapes and host buffers; the assembly inherited
   every simplification. Inference engines are built the other way: a
   device-resident program with one end-to-end oracle from day 1, then op by
   op replaced/optimized under that oracle.
5. **Monolith.** `compute.rs` is 4.4K lines mixing model config, weight
   containers, dequant, per-op FFI wrappers, the forward pass, graph plumbing
   and artifact routing. Split is needed anyway once the forward moves to
   C++.
6. **Docs are consistent with each other but not with the code.** CONTEXT.md
   / design doc describe a target architecture as if built. ADR 0008
   (staging-buffer graphs) solves a problem the real design won't have (the
   graph must carry per-slot KV/state views, batch-width variants, and
   per-step token/position inputs — ninfer's `decode_graph.cpp` model).

## 5. Reorganization: what to keep, what to change, what to delete

### 5.1 Keep (with re-wiring)
- `crates/artifact` — the reader/binder/checksum/frontend are the strongest
  asset. Add: a device-side view API (plane pointers + layout descriptor) that
  the C++ program consumes directly; drop the host-side W8 dequant once a W8
  GEMV lands.
- `crates/server` — API, SSE, telemetry. Add EOS/stop, sampling params
  plumbing, request-log JSONL (ninfer's `--request-log-jsonl` is what the
  bench and the user rely on).
- `crates/core` scheduler/admission/host-tier/prefix — keep as the control
  plane, but each abstraction must own a **handle to device state** (page
  ids that are real device pages; a GDN slot id; a pinned-host snapshot
  region). The `Compute` trait is replaced by a step-level device runtime
  handle (§5.3).
- `crates/bench` — keep; it is the gate tool.
- `docs/adr` 0002, 0004, 0005, 0006, 0007 — still valid. 0001 revised
  (ABI granularity). 0003 already superseded. 0008 superseded.

### 5.2 Delete / park
- `compute.rs` forward path (`forward_layers`, `forward_layers_multi`,
  `prefill_*`, `decode*`, `state_readout`, host glue) — replaced, not fixed.
- `kernel/src/decode_graph_surface.cu`, `graph_capture.cu` (toy sequence),
  `hello.cu`/`vector_sum`, every `*_surface.cu` with host-pointer contracts.
- The scalar kernels (`nvfp4_gemm_*.cuh`, `gqa_attention_*.cuh`,
  `gdn_step.cuh`) — replaced by real ports. Their f32 CPU references in tests
  can be reused as oracles for tiny shapes only.
- The parked `gdn-step-dk-tiling` worktree (keeps the dead-end flat ABI).

### 5.3 The new shape (the decision to make)

```
crates/server   HTTP, OpenAI/Responses, streaming, tokenizer/chat template, telemetry
crates/core     scheduler, admission, KV page accounting, prefix index, host tier policy
crates/artifact reader / binder / checksum / device materializer (arena)
crates/runtime  (new, thin)  safe Rust wrapper over the step-level C ABI below
kernel/         C++/CUDA "program" layer + ops + tests (its own CMake test binary)
```

Step-level C ABI (device-resident, opaque handles, no host activations):

```
ignis_model_load(arena_view, config) -> model
ignis_seq_alloc(model, max_ctx) -> seq          // KV pages + GDN slot + conv state, on device
ignis_seq_release / ignis_seq_snapshot(host_pinned) / ignis_seq_restore
ignis_prefill(model, seq, tokens[n], pos0, chunk) // chunked; returns last logits (device) or sampled id
ignis_decode(model, seqs[B], tokens[B]) -> ids[B] // one batched round; CUDA-graph per B
ignis_sample_params(...)                         // greedy / temp / top-p / top-k / penalties
ignis_kv_pages_*                                 // page table ops the core's KvPool drives
ignis_stats(...)                                 // kernel counts, graph hits, VRAM
```

The forward pass (the per-layer op sequence: norm → proj → conv → gating →
recurrence → gated norm → out-proj → residual → norm → gate_up → silu_mul →
down → residual) lives in C++, on streams, with device tensors, captured into
a graph per decode batch width. This is what ninfer's
`text_context_impl.h` + `decode_graph.cpp` + `concurrent_executor.h` do. Rust
orchestrating 630 device-pointer launches per round through FFI is possible
but buys nothing and costs the graph capture ergonomics; the ABI boundary
belongs at the step.

This revises ADR 0001's "Rust owns everything above compute": Rust owns
everything above the **step**, C++ owns the step.

### 5.4 Kernel policy (the second decision)

ADR 0005 says "port proven kernels for now, re-implement later." What was
shipped is neither. Options:

- **(A) Port ninfer's kernels verbatim** — the `.cuh` files, their launch
  helpers, and their storage-layout decoders (`nvfp4_codec.cuh`,
  `nvfp4_gemv.cuh`, `nvfp4_small_t.cuh`, `nvfp4_w4a4_*`,
  `gqa_attention_{decode,prefill}_*`, `recurrent.cuh`, `chunked/*`,
  `causal_conv1d.cuh`, `gdn_gating.cuh`, `rmsnorm.cuh`, `l2norm.cuh`,
  `rope.cuh`, `hq_codec.cuh`, `sampling*.cuh`, `mtp_*`, `dflash2_draft.cuh`).
  Apache-2.0 → allowed with NOTICE (already present). The "dispatch layer is
  C++ state the ABI forbids" argument in the kernel headers was a
  misunderstanding: the dispatch stays *inside* the leaf; only the step ABI
  crosses the boundary.
- **(B) Write our own tensor-core kernels** — months per family to reach
  ninfer's numbers (their W4A4 TMA GEMM alone is a long-tuned piece).

Recommendation: **(A) now**, which is what ADR 0005 already says; (B) later
per family, gated by measurement, as the north-star work. Where ninfer is
at roofline (BF16 GEMV, int8 decode attention, GDN chunked prefill —
`ROADMAP-kernel-perf.md` §0) there is nothing to gain from (B) at all.

## 6. Path to a usable engine (≥ ninfer), with hard gates

Every phase ends in a **GPU-measured gate**. No phase is "done" on CPU tests.
Order is by dependency, not by ticket size.

### Phase 0 — Reset the ground truth (≈1 week)
- Rewrite README status, PENDING (open: "no working forward"), CONTEXT.md
  (add: GDN head structure 48V/16K ×128 fp32, hq-e8-2b, chunked prefill,
  batched decode round, decode graph per width), design doc §3 milestones.
- ADR 0009: step-level device-resident ABI (supersedes the per-op host-pointer
  contract; revises 0001). ADR 0010: kernel policy = verbatim port with
  provenance (clarifies 0005). Mark 0008 superseded.
- **Oracle.** Build the per-layer numeric oracle before any kernel work:
  run ninfer (`tools/reference`, `tools/parity`, or a small C++ harness
  linking ninfer's ops) on 3 canary prompts, dump per-layer hidden states +
  final logits for the first 32 tokens to disk. This is the acceptance
  instrument for Phases 1–2.
- **GPU-in-the-loop test rule.** A `gpu` test profile that *fails* (not
  skips) when the GPU is busy; run it explicitly by the human/gate, never in
  the default `cargo test`. Kernel leaf gets its own C++ test executable
  (ninfer `tests/ops` style) so ops are checked without Rust.

### Phase 1 — Correct device-resident forward, batch 1, bf16 KV (≈3–5 weeks)
Gate **G1**: greedy completions on the canary suite are coherent text; per-
layer max-abs error vs the oracle within bf16 tolerance; logits argmax agrees
on ≥ 95% of the first 32 tokens (self-check, not a parity gate — ADR 0007).
- Leaf: device arena/tensor, streams, layer program (`text_context`
  equivalent), sequence state (KV pages, GDN fp32 slot pool
  `[48][48][128][128]`, conv taps).
- Ported ops (decode shapes first): NVFP4 GEMV with the blockscale decoder +
  divisor; BF16 GEMV; W8G32 GEMV (lm_head, embedding gather); rmsnorm;
  per-head q/k norm + RoPE (θ=1e7, verify NeoX vs interleaved against the
  oracle); GQA decode attention (bf16 paged); causal_conv1d+SiLU; gdn_gating;
  GDN recurrent step (per-head, fp32, L2-normed q/k, 1/√128); gated
  rmsnorm; silu_and_mul; residual; argmax.
- Prefill in this phase: per-token recurrence is acceptable *only* to reach
  G1 (it is what makes the oracle comparable); Phase 2 replaces it.
- Rust: `crates/runtime` wrapper; server end-to-end on one request; EOS.

### Phase 2 — Real prefill (≈2–3 weeks)
Gate **G2**: TTFT at 8K / 32K prompts ≤ 1.5× ninfer MTP0 (ninfer: ~8.5K tok/s
@24K → ~2.9 s); oracle still green.
- Chunked prefill (1024) with: W4A4 activation quant (site divisors) + the
  W4A4 MMA/TMA GEMM; `nvfp4_small_t` for small T; bf16 tensor-core prefill
  attention with KV append; GDN chunked kernels (`prepare_wy_wu`,
  `state_passing`, `output`); shared-prefix boundary hook (for Phase 4).

### Phase 3 — Serving loop: batched decode + graphs + sampling (≈2–3 weeks)
Gate **G3**: C=1 MTP0 decode ≥ 99% of ninfer's 75–76 tok/s; C=4 aggregate
≥ 99% of ninfer's C=4; p95 inter-token latency while another request
prefills within ninfer's envelope.
- One batched decode round for all decode-ready lanes (ninfer §2.1); CUDA
  graph captured per batch width at startup (eager for uncaptured widths);
  PDL where the ported kernels support it.
- Sampling: greedy, temperature, top-p, top-k, presence penalty; seed.
- Core re-wired: `KvPool` pages are device pages; admission's capacity
  math uses real bytes; `GdnState` boundaries map to real slot checkpoints.
- Telemetry + request-log JSONL with per-request phase rates (the bench's
  input).

### Phase 4 — ninfer feature floor (≈3–4 weeks)
Gate **G4**: the bench-03 99% gate on the recorded "1 main + N subagents"
trace, hq-e8-2b on both sides; needle-retrieval sanity at 64K/128K.
- hq-e8-2b KV (`hq_codec.cuh`, hq attention variants, exact-key side store)
  — the profile the user runs.
- Prefix reuse on device (page refcount → real page sharing; shared
  system+tools boundary capture).
- KV-RAM host tier with real pinned-host snapshot/restore (incl. GDN slot,
  conv taps, side store — ninfer's header v2 sections are the checklist of
  what must be captured).
- Tagged lanes (`@main/@agents/@classifier`), preserve-thinking, tool-call
  parsing hardening (ninfer's streaming fixes), warmup/readiness split.

### Phase 5 — Speculative decoding (≈3–4 weeks)
Gate **G5**: ≥ 99% of ninfer's MTP7-adaptive / DFlash2-7 committed tok/s at
24K / 98K / 196K (150 / 104–132 / 79–144 tok/s per `SEPT-OPTIMIZAZION.md`).
- MTP first (single MTP layer already in the artifact; `mtp_round`,
  `mtp_pack`, adaptive width controller, ReplaySSM records for GDN rollback).
- DFlash2 second (5-layer drafter module load from the v2 artifact,
  `dflash2_draft.cuh`, RAM-tier KV carry for the drafter).
- Vision is *not* on the floor for a coding engine; defer past G5.

### Phase 6 — Beyond ninfer (the north star)
Only after G4/G5: concurrent prefill across requests / prefill-decode overlap
(ninfer explicitly does not do this — the real differentiator for subagent
bursts), fusion + PDL everywhere (`ROADMAP-kernel-perf.md` WI-K2: −1 ms/step),
lazy graph capture, hot reload, our own NVFP4 artifact recipe, lane QoS.

Rough total to G5: **14–20 weeks** of focused work. To G3 (a usable
single-user local engine at ninfer MTP0 speed): **7–11 weeks**.

## 7. Decisions needed from the owner

1. **ABI level:** step-level device-resident C ABI with the forward in C++
   (recommended) vs Rust-orchestrated device ops. → ADR 0009.
2. **Kernel policy:** verbatim port of ninfer ops with provenance
   (recommended, Apache-2.0, NOTICE exists) vs own kernels first. → ADR 0010.
3. **Reset scope:** delete the compute.rs forward + toy graphs now (recommended;
   they mislead every future reader) vs keep behind a feature flag.
4. **Oracle source:** ninfer per-layer dumps (recommended; same artifact,
   same numerics) vs an HF/PyTorch reference (needs a second GPU-sized
   environment; not available on this box).
5. **First KV dtype:** bf16 for G1–G3, hq-e8-2b at G4 (recommended) vs hq
   from the start.
6. **Process:** GPU gate per compute ticket with a named oracle check; retire
   "skip = green" for compute; kernel leaf gets its own test binary. Agent
   tickets are cut per *op family under the oracle*, not per "surface".
